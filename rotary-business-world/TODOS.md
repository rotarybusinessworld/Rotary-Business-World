## Week 1–2 (Before or alongside auth rewrite)

### ~~🔴 [P0 Security] Suspended admins bypass suspension via `requireAdmin()`~~ ✅ FIXED 2026-08-16

**File:** `src/backend/auth-helpers.ts:76–97`

`requireAdmin()` reads live role from actor cache and redirects on revocation — correct.
But it never checks live **status**. A suspended DISTRICT_ADMIN or MANAGEMENT user:
1. `requireUser()` only blocks them if JWT says SUSPENDED (stale for up to 30 days)
2. `requireAdmin()` checks `snapshot.role` — still DISTRICT_ADMIN (suspension ≠ role change)
3. They pass → full access to `/admin/verifications`, `/admin/listings`, `/admin/members`

Same gap in `requireManagement()` — checks JWT role only, no actor cache read at all.

**Fix:** In `requireAdmin()`, after `getActor()`:
```ts
const liveStatus = snapshot?.status ?? user.status;
if (liveStatus === "SUSPENDED") {
  await unstable_update({ user: { status: "SUSPENDED" } });
  redirect("/account/suspended");
}
```
In `requireManagement()`: add a `getActor()` call with the same status check.

**Note:** This is resolved automatically when magic-link auth + the `getActor()` architecture
lands (Tier 1 #2), since JWT staleness disappears. But the fix above is 4 lines and
should land before launch regardless.

### ~~🔴 [P1 Correctness] Webhook idempotency gate blocks retries after a crash~~ ✅ FIXED 2026-08-16

**File:** `src/app/api/razorpay/webhook/route.ts:63–78`

The `WebhookEvent` row is inserted (status=RECEIVED) before `settlePayment()` runs.
If `settlePayment()` throws (DB timeout, transient error), the event stays RECEIVED.
Razorpay retries → sees count=0 (event already exists via `skipDuplicates`) → returns 200
immediately without calling `settlePayment()`. After Razorpay's 4 retry attempts, the
payment is permanently unprocessed. Member paid, never gets verified.

`settlePayment()` is already idempotent (checks CAPTURED inside transaction). The
WebhookEvent early-exit should gate on status=PROCESSED, not existence.

**Fix:**
```ts
const existing = await db.webhookEvent.findUnique({
  where: { eventId },
  select: { status: true },
});
if (existing?.status === "PROCESSED") return NextResponse.json({ received: true });

if (!existing) {
  await db.webhookEvent.create({ data: { provider: "razorpay", eventId, eventType: event.event, payload: event as object, status: "RECEIVED" } });
}

await settlePayment({ ... }); // idempotent — safe to call on retry
await db.webhookEvent.update({ where: { eventId }, data: { status: "PROCESSED", processedAt: new Date() } });
```

## Week 3 (Alongside rate limits + idempotency)

### ~~🟠 [P2 Performance] `requireVerified()` calls `getActor()` twice for PENDING_VERIFICATION users~~ ✅ FIXED 2026-08-16

**File:** `src/backend/auth-helpers.ts:50–69`

`requirePaid()` (called inside `requireVerified()`) already reads the actor snapshot and
returns `{ ...user, status: liveStatus }`. `requireVerified()` then calls `getActor()` again
for PENDING_VERIFICATION users — a redundant Redis/Postgres round-trip. This hits the largest
user cohort during launch week (every member between paying and getting approved).

**Fix:** Return the snapshot from `requirePaid()` alongside the user, and read from it in
`requireVerified()` instead of calling `getActor()` again.

**File:** `src/app/(main)/business/[slug]/page.tsx:34–47, 64–72`

`generateMetadata()` and the page component both call `getBusiness(slug)`, which hits
Postgres with the same 4-table join twice per page load. Fix is one import:

```ts
import { cache } from 'react';
const getBusiness = cache(async (slug: string) => db.business.findUnique({ ... }));
```

`react.cache()` deduplicates calls with the same argument within a single request render tree.
